How it works

The pipeline has three moving parts and one data contract. This page is the third part — the demo data below it is exactly what part two emits for a real project.

1 · Scanner

A zero-dependency Node script (scan-and-generate.mjs) walks your source tree with pure regex: imports, classes, methods, descriptions. No AST, no LLM, no API keys.

2 · Generator + cache

Emits one data file (js/arch-data.js) — the single source of truth. An incremental mtime+size fingerprint cache makes re-runs ~130 ms; --no-cache forces a full rescan.

3 · Viewer

A single HTML page (this one) renders tag cloud → depth button → Mermaid flowchart. Click to drill, search to filter, hash deep links for sharing. No build step, no backend.

The renderer — Mermaid 11

Every diagram on this page is drawn by Mermaid, a free, MIT-licensed library that turns plain text into SVG diagrams — flowcharts, sequence diagrams, class diagrams and more. You write engine.ts --> fuel-injection.ts and Mermaid lays out and draws the chart in the browser. It loads from a CDN (https://cdn.jsdelivr.net/npm/mermaid@11.12.0/dist/mermaid.min.js), needs no build step and no backend, and works straight from file:// — which is exactly why the whole system is just static files you can open or publish anywhere. The prompt tells the agent to feed the scanned data to Mermaid and style it (custom palette, depth colors, flowing-edge animations), so every generated chart follows the same look.

LLM-based generation — when dynamic scanning isn't possible

Dynamic scanning is the default, but it has requirements: the project needs source code that a regex scan can capture. If those requirements aren't met — a small project, or a language the scan can't handle — the prompt supports LLM-based generation instead of stopping: it builds the same viewer in static mode, tells you that only static flowcharts are possible, and adds a 🔄 Regenerate flowcharts button that redraws them using an API key you provide (e.g. Google AI Studio — Gemini 3.1 Flash). This path runs only with your approval — your key, your call; nothing ever calls out to an LLM without it, and the key never leaves your browser except to the provider you chose.

Why flowcharts matter — and how they make you build better

Code is the most detailed description of a system ever written — which is exactly why it hides the big picture. A flowchart is the big picture: one glance at a diagram shows what a hundred files only reveal after hours of reading. Here's what that buys you in practice.

🗺 See the real shape of your system

Every project has a plan in someone's head and a reality in the code — and those two drift apart the moment the plan is written. An auto-generated flowchart can't drift: it is the code, drawn as a map. You see at a glance what depends on what, where the layers are, and whether the architecture you designed actually survived contact with the codebase.

🎯 Find what to optimize

  • Hot modules — a module many others import. Every change to it ripples outward; it's the highest-risk, highest-value place to invest (stabilize its API, split it, or put a cache in front of it).
  • Cycles — A imports B and B imports A. Circular dependencies break clean layering and signal a missing abstraction; the diagram shows them as loops you can't unsee.
  • God modules — one module with dozens of classes or hundreds of methods: split candidates, found at depth 3 in one click.
  • Dead code — modules nothing imports: the diagram lists them for deletion.
  • Layering violations — infrastructure leaking into everything, or the database importing the UI. The overview exposes the boundaries you thought you had.

🏗 Build systems correctly from day one

  • Before you write a feature, check the diagram for everything it touches. If the change reaches into a hot module or crosses a layer boundary, that's a design decision — make it on purpose, not by accident.
  • After a refactor, regenerate and diff the diagram. New edges you didn't intend are the first, cheapest signal that an abstraction is wrong.
  • Onboarding — a new developer reads the map in five minutes and finds the right file in five more, instead of spelunking for a week.
  • Code review — review the diff against the diagram: does the change respect the architecture the picture shows?
  • Depth on demand — the same map serves the architect (overview), the implementer (classes and methods), and the debugger (method internals and component effects). One system, five zoom levels, no separate docs to keep in sync.

In one sentence: a flowchart generated from the code gives you a map of the city that actually got built — so you can optimize the right streets, and never accidentally route a highway through someone's living room.
